# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A desktop-pet-style game built on pygame: an NPC pet with hunger/thirst/boredom/tiredness needs and a passive happiness meter, driven by a small PyTorch DQN (deep Q-network) agent that learns to walk toward whatever target the pet currently needs (food, water, a toy (ball or bone - interchangeable kinds of the same mechanics), a spot the player has called it to, or - when nothing's urgent - a self-initiated idle activity like wandering, napping on its bed, grabbing a toy from its toybox, or playing fetch). Fetch is teachable, not just personality-fixed: petting the pet shortly after it delivers a toy reinforces fetch as a favorite over playing alone, decaying back down if not kept up. It's also a scored mini-game: every delivery earns the player currency (streak-multiplied, commanding a round via the right-click "Fetch" option pays more than an autonomous one), tracked in a wallet that belongs to the player, not any one pet (see `wallet.py`). The pet also communicates via species-specific speech-bubble vocalizations (bark/growl/whine/howl for the current dog, onomatopoeia + an emotion emoji) driven by a small mutually-exclusive emotion read of its state, kept in a separate per-species vocabulary file so a future cat or robot doesn't inherit the dog's bark - plus a species-agnostic "ZzZzZz" sleep bubble whenever it's actually settled at the bed. The pet is rendered with an animated sprite (temporary placeholder art). Progress persists across sessions per named pet. Personality (Big Five traits) has its first real hook into behavior via idle-activity weighting (see npc.py's Personality bullet below) - the long-term goal is a cross between a desktop pet and an actual game, with personality eventually affecting more of how the pet behaves toward the player and other NPCs, plus a currency/mini-game/cosmetics layer planned on top (see README's Roadmap).

## Commands

There is no build system, package manifest, or test suite — run scripts directly with the venv's Python.

```bash
# Run the game (opens a window at the main menu)
.venv/bin/python virt-pet.py
```

See `CONTROLS.txt` for the full, current control scheme (menu/pause/load screens, in-game controls) — keep it updated when controls change.

The `.venv` directory (Python 3.14) already has `pygame`, `torch`, and `numpy` installed. There is no `requirements.txt`; if adding dependencies, install them into `.venv` with `.venv/bin/pip install <pkg>`.

There's no automated test suite. The working pattern used throughout development is a headless smoke test: `pygame.init()` + `set_mode(...)`, construct the objects, call `.update()` in a loop with synthetic inputs, and assert on the resulting state (e.g. `pet.hunger`, `pet.target_pos`, `pet.active_need`). This works even without a real display attached. For validating `virt-pet.py`'s event/state-machine logic specifically, drive the actual script end-to-end with `pygame.event.post(...)` synthetic events + `runpy.run_path("virt-pet.py", run_name="__main__")`, rather than reimplementing its logic in a test — this has caught real bugs (e.g. a stale per-frame cache that only broke when two menu clicks landed in the same event batch).

## Architecture

- **`virt-pet.py`** — pygame entry point. Owns the game loop and a small state machine: `STATE_MENU` → `STATE_PLAYING` ⇄ `STATE_PAUSED` → `STATE_LOAD`.
  - **Menu**: hand-rolled text box to name the pet (pygame has no built-in text input) — keystrokes are filtered to alnum/space/-/_ as you type. Start constructs `npc(name, screen)`, which auto-loads a save if one exists under that name.
  - **Playing**: calls `pet.update(dt, food.pos, water.pos, toy_pos, bed.pos, toy_on_ground, mouse_pos, toybox.pos)` every frame, then reacts to five one-frame output signals the pet can raise (mirroring the `called`/`call_pos` input pattern, but pet → game instead of player → pet) before `draw_scene()`: `pet.wants_to_throw_toy` (self-play decided to throw — same random-velocity `toy.throw()` the pet always uses, vs. the player's deterministic `toy.throw_toward()` below), `pet.wants_toy_from_box` (the `"get_toy"` idle activity grabbed one — `toy.active = True; toy.place(TOY_DEFAULT_POS)`), `pet.carrying_toy` (mid-fetch — `toy.pos` is set to `pet.mouth_pos()` every frame instead of running `toy.physics_update()`, so the toy visually rides along; `toy.physics_update()` is itself skipped while carrying), `pet.wants_to_drop_toy` (fetch delivered, or a carry got interrupted — `toy.place()`s it at the pet's feet, then cleared), and `pet.fetch_delivered` (a delivery just earned coins — `wallet.earn(pet.fetch_reward_amount)`, then both cleared). Right-click opens a context menu (`context_menu_pos`, recomputed fresh via `context_menu_entries()` rather than cached — same fix as the load-screen bug below) with "Call" (`pet.call_to()`), "Pet" (`pet.pet_interact()`), and "Fetch" (`pet.request_fetch()` — see npc.py's Idle-time bullet for what that actually triggers) options; while the menu is open it swallows that frame's clicks/Esc instead of falling through to normal play controls. Petting lives *only* here, not on a direct pet click — the pet is drawn topmost every frame, so a left-click would always win on any overlap (e.g. a toy just fetched to its feet), the same problem the food/water click-priority fix solved, but unfixable here by reordering since the pet is legitimately on top; moving it to a different mouse button/menu sidesteps it instead. Clicking the toybox (a static item, `toybox.contains_point()`) opens a second, differently-anchored menu the same way (`toy_menu_open`/`toy_menu_anchor`/`toy_menu_entries(anchor)`, anchor computed fresh above the toybox each time it opens, sized off `len(TOY_MENU_OPTIONS)` so it grows with more kinds) — `TOY_MENU_OPTIONS` labels lowercase directly to `item.kind` (`"Ball"` → `toy.kind = "ball"`, etc.); picking the kind already out again toggles it off (`toy.active = False`), picking a different kind while one's out swaps it (`toy.kind = kind; toy.place(...)`) instead of requiring two clicks, and picking one when nothing's out just brings it out at rest (`toy.place(TOY_DEFAULT_POS)`, positioned just off the toybox). Clicking the toy itself while `toy.on_ground` (via `item.contains_point()`, a circular hit-test) throws it via `toy.throw_toward(event.pos)` — deterministic from click position, unlike the pet's own random self-play throw (see items.py). Clicking the food/water items feeds/waters the pet instantly (`pet.feed()`/`pet.give_water()`, via `item.get_rect()` hit-testing) regardless of the pet's position. Click-priority order in code matches `draw_scene()`'s z-order (toy topmost among items, then the toybox/static items underneath) for the same overlap reason as food/water/toy previously. Esc (when neither menu is open) opens the pause menu. `draw_scene()` also draws `draw_wallet()` (a coin counter, top-right, roughly where the old fixed "Toys" button used to be) every frame regardless of pet state, since the wallet isn't pet-specific.
  - **Paused**: draws the frozen scene (via the same `draw_scene()`, but `pet.update()` is not called, so the world/animation stops) with a semi-transparent overlay and Resume/Save/Load/Back-to-Main-Menu buttons.
  - **Load**: lists other saved pets by scanning `saves/*.json` (`list_saved_pets()`); picking one saves the current pet first, then constructs a new `npc(other_name, ...)`. The module-level `wallet = Wallet()` is created once at script start and is untouched by `start_pet()`/Load - switching pets never resets currency, by design (see `wallet.py`).
  - Saves happen on: autosave (every `AUTOSAVE_INTERVAL` seconds), the Save button, Back-to-Main-Menu, Load (of the outgoing pet), window close, and Esc-from-menu — all wrapped in `safe_save()`'s try/except so a save error never blocks shutdown/transition.
- **`npc.py`** — the `npc` class, the pet itself. Nearly all game logic lives here:
  - **Needs**: `hunger`, `thirst`, `boredom`, `tiredness` each climb every frame (tiredness at different rates depending on `TIREDNESS_RATE_ACTIVE`/`_IDLE`, i.e. whether the pet moved or played that frame), capped at 100, and drain via proximity (food/water/toy/bed, all gated on `interact_radius`) once the corresponding need is `active_need`. Tiredness's target is the bed (`bed_pos`, falling back to the pet's own position if somehow `None`) — same "walk there, then recover" shape as hunger/thirst, not a special case anymore.
  - **Happiness** is different: not a need the pet seeks out, just a passive 0–100 meter that decays when ignored and rises from playing near the toy or from `pet_interact()` (click-to-pet, cooldown-gated via `_pet_cooldown`).
  - **Target selection** (`choose_target`): decides what the pet is currently walking toward, with hysteresis via `self.active_need` — once a need crosses its seek threshold and becomes the active pursuit, the pet keeps heading for it (even if the value dips back under the threshold) until it drops below `satiated_threshold`. Becoming urgent, or the player calling the pet (`self.called`/`self.call_pos`, set by the right-click "Call" option), both abandon any in-progress idle activity via `_abandon_idle_activity()`. A pending call is deferred, not dropped, by an urgent need: `choose_target` only reaches the call/idle branch when no need is urgent, so `self.called` stays `True` (and the call target still queued) until the need is handled; it's cleared once the pet arrives with `self.active_need is None` (see `update()`). When nothing is urgent and it hasn't been called, it does *not* follow the mouse — it falls through to `_tick_idle()`, returning `self.idle_target`.
  - **Idle-time self-initiated behavior** (`_tick_idle`/`_pick_idle_activity`/`_idle_weight`/`_abandon_idle_activity`): instead of standing frozen whenever nothing is urgent, the pet runs its own small activity loop. `_pick_idle_activity()` first checks `self.fetch_requested` (set by `request_fetch()`, the right-click "Fetch" option) — if set, it **overrides** the weighted roll entirely: forces `"fetch"` straight away if a toy's ready (also setting `self.fetch_commanded = True` and consuming the request), or forces `"get_toy"` first if not (leaving `fetch_requested` set, so the *next* pick - once `wants_toy_from_box` has been acted on and a toy exists - resolves to fetch automatically with no extra chaining code needed). `self.fetch_commanded` is reset to `False` at the top of every pick, so a delivery's reward always reflects how *that* round actually started. Otherwise, when `self.idle_activity` is `None`, it rolls a personality-weighted choice (`_idle_weight()` — see Personality below) among `"stand"`/`"wander"`/`"bed"` (if `bed_pos` given) / `"self_play"`+`"fetch"` (if a toy is out and `toy_on_ground`) / `"get_toy"` (if no toy is out but `toybox_pos` is given — walking to the box to grab one *instead of* self_play/fetch, which need an actual toy already present); picking anything other than `"fetch"`/`"get_toy"` here resets `self.fetch_streak = 0` (see Personality/fetch mini-game below) since that's the chain breaking, not just standing between rounds. Each choice sets `self.idle_target` and a randomized `self._idle_hold_timer` range (`IDLE_*_HOLD` constants). Every subsequent frame: if the toy the pet is mid-`"self_play"`/`"fetch"` with vanishes (`toy_pos` goes `None` — e.g. toggled off from the toybox), the activity is abandoned immediately rather than marching toward or "delivering" nothing. Otherwise, once horizontally arrived at `idle_target` (same `arrival_radius` check as everything else), the hold timer counts down; when it expires the activity resolves: `"self_play"` sets `self.wants_to_throw_toy`; `"get_toy"` sets `self.wants_toy_from_box` (see Playing above for both); `"fetch"` has two sub-phases tracked in `self._fetch_phase` — `"pickup"` (walk to the toy, then flip to `"deliver"`: sets `self.carrying_toy = True` and re-targets `mouse_pos`, live-tracked every frame while delivering rather than fixed at pickup time) then `"deliver"` (arriving at the player sets `self.carrying_toy = False`, `self.wants_to_drop_toy = True`, opens `self._fetch_reward_window` — see Personality/fetch training below - increments `self.fetch_streak`, computes `self.fetch_reward_amount` via `_fetch_reward()`, and sets `self.fetch_delivered = True`); anything else (`"stand"`/`"wander"`/`"bed"`) just resets `self.idle_activity = None` so the next frame picks again. `_abandon_idle_activity()` also resets `fetch_streak`/`fetch_commanded` when it interrupts an in-progress `"fetch"` - an incomplete delivery breaks the streak same as choosing something else would have. `mouth_pos()` gives virt-pet.py roughly where to render the carried toy.
  - **Movement/RL**: `update()` builds a 4-value state `[pet.x, pet.y, target.x, target.y]` (normalized 0–1), gets an action from `self.agent` (0: left, 1: stay, 2: right), and moves — but only if not within `arrival_radius` of the target horizontally; inside that radius `self.move` is forced to `0` (stands still) regardless of the network's pick, rather than relying on the network having converged on that behavior. Reward reflects only the pet's own contribution to closing the distance (measured before/after its own move against the same frozen `target_pos`), not the target moving on its own. Training happens online, every frame, via `agent.remember()` + `agent.replay()`. Note the RL loop only ever learns "walk toward this x/y" — self-play/fetch/etc. are plain Python state machines built on top of it, not something the network itself decides.
  - **Personality**: `open`/`conscient`/`extravers`/`agreeable`/`neuroticism` (Big Five, 0–10 scale), randomized per-instance in `randomize_personality()` — but only when no save exists for that name (see persistence below). First real hook into behavior: `_idle_weight()` weights idle-activity selection by trait (`conscient` → `"bed"`, `open` → `"wander"`, `agreeable`+`extravers` → `"fetch"`/`"get_toy"` — sociable pets would rather play *with* you than alone, `neuroticism` → `"stand"`, i.e. anxious pets move around less; `"self_play"` carries no trait bonus, it's the personality-neutral default when nothing else pulls harder) — every trait maps to something, but nothing is ruled out entirely, just made more/less likely. **Fetch is additionally trainable**, not just personality-fixed: `_idle_weight("fetch")`/`"get_toy"` also adds `self.fetch_affinity` (persisted, capped at `FETCH_AFFINITY_MAX`), which `pet_interact()` bumps by `FETCH_AFFINITY_REWARD` if petting happens while `self._fetch_reward_window > 0` (opened for `FETCH_REWARD_WINDOW` seconds by a completed fetch delivery, consumed by the first pet within it — no stacking), and which decays every frame in `update()` at `FETCH_AFFINITY_DECAY_RATE`/sec if not reinforced — a taught habit that fades without upkeep, not a permanent switch. **Fetch mini-game reward** (`_fetch_reward()`, called at delivery time from `_tick_idle`): looks up `self.fetch_streak` in `FETCH_STREAK_REWARDS` (flat for the first couple of deliveries, then ramping up fast - `[5, 5, 6, 15, 45]`), or beyond that list keeps multiplying the last entry by `FETCH_STREAK_GROWTH` per extra streak step; a commanded delivery (`self.fetch_commanded`) pays that in full, an autonomous one pays `FETCH_AUTONOMOUS_REWARD_RATIO` (0.5) of it, `round()`ed. `fetch_streak`/`fetch_commanded`/`fetch_requested` are **not** in `PERSONALITY_FIELDS` - transient per-session state, not persisted (unlike `fetch_affinity`, which is the *learned preference*, a separate concept from the *scoring* streak). Everything else about the pet (need thresholds, happiness decay, the vocalization emotion thresholds below, etc.) is still trait-independent - that's the next surface to wire up (see README Roadmap).
  - **Vocalizations** (`_current_emotion`/`_try_vocalize`/`_tick_vocalization`, vocab in `vocalizations.py`): a speech bubble (onomatopoeia + emotion emoji) the pet shows for `VOCAL_DISPLAY_TIME` seconds, on a randomized `VOCAL_COOLDOWN` so it doesn't spam. `_current_emotion()` reads `happiness`/`active_need` into one of `"angry"`/`"sad"`/`"lonely"`/`"happy"`/`None`, checked **in that priority order and mutually exclusive** — e.g. happiness below `ANGRY_HAPPINESS_MAX` reads as angry even if an urgent need is also active, so a badly-neglected pet growls instead of whining; `"sad"` additionally requires an urgent physical need (hunger/thirst/tiredness), so boredom alone doesn't trigger it. `_tick_vocalization()` (called every frame from `update()`) is the periodic path for these three, but bails out early (also clearing any leftover `self.vocalization`) whenever `self.anim_state == "sit"` — asleep pets don't vocalize complaints, see the sleep bubble below; `_try_vocalize("happy")` is also called directly at specific excited moments (`pet_interact()` success, arriving from a Call, the self-play throw, and fetch's pickup) rather than waiting for the periodic scan, though it's still cooldown-gated like everything else. `self.species` (currently always `vocalizations.DOG` — hardcoded, not yet a real per-pet choice) looks up `vocalizations.VOCABULARY[species][emotion]`; a species/emotion with no vocab entry is a silent no-op by design, so a future non-dog species never inherits the bark unless it's given its own entry. Both this and the sleep bubble share `draw()`'s `_draw_bubble(label)` for the bubble chrome, rendered via a lazily-created module-level font cache (`_bubble_font()`, same lazy-after-`pygame.display.set_mode()` reasoning as `_load_sprite_frames()`).
  - **Sleep bubble**: `draw()` shows a `"ZzZzZz"` bubble (via the same `_draw_bubble()`) whenever `self.anim_state == "sit"`, which — now that tiredness's target is the bed (see Needs above) — only ever fires once the pet is actually settled at the bed, whether that's urgent tiredness recovery or the proactive `"bed"` idle activity (see below); no separate "am I asleep" flag needed.
  - **Sprite animation**: `_load_sprite_frames()` lazily slices `DogBundle/PNGs/Corgi.png` (512×192, 8 cols × 3 rows of 64×64 frames: walk/idle/sit) into a `{"left"/"right": {"walk"/"idle"/"sit": [frames]}}` cache — lazy because it needs `pygame.display` already initialized, which happens after `npc.py` is imported in `virt-pet.py`. The sheet's native orientation faces **right**; frames have ~16px of transparent padding below the paws (`SPRITE_BOTTOM_PADDING`), compensated for in `draw()`'s ground anchor. `_advance_animation()` picks walk/idle/sit from `self.move`/`self.active_need` (idle covers eating/drinking — there's no dedicated animation for those) and only updates `facing_left` while actually moving. Only Corgi is wired up; the other 4 breeds in `DogBundle/PNGs/` are unused.
  - **Persistence**: `save()`/`load()` write/read `saves/<name>.pt` (DQN weights + optimizer + epsilon, via `NPCAgent.save`/`load` in `npc_net.py`) and `saves/<name>.json` (personality + all the need-tuning knobs in `PERSONALITY_FIELDS`). `npc_name` can come from free-text player input in the menu, so **never use it raw in a filesystem path** — `_safe_name()` strips it to alnum/space/-/_ first (defense against e.g. a pet named `../../etc`); this was a real fix made when the menu was added, not a hypothetical.
- **`items.py`** — the `item` class for food/water/bed/toybox/toy. `pos` is always the item's ground-contact point (equivalent to `midbottom`), not its center. The bed and toybox are static (always drawn, like food/water — no active/inactive toggle); the bed is purely a location for the pet's "bed" idle activity and isn't clickable, the toybox is clickable (opens the toy menu) but doesn't move. `get_rect()` returns the same rect `draw()` renders (food/water/bed/toybox), reused for click hit-testing so the clickable area always matches what's on screen; `contains_point()` is the click hit-test proper — a circular check for the toy (its `get_rect()` bounding box would catch clicks in the circle's corners), `get_rect().collidepoint()` otherwise. `place(pos)` resets an item to a resting position with no throw in flight (used when a toy is brought out from the toy menu or the toybox-idle-activity, and when a fetch delivery/interruption drops it — see npc.py's Playing bullet). The toy additionally supports throw physics: `throw(velocity)` launches it with a given velocity (used for the pet's own random self-play/fetch throws), `throw_toward(click_pos)` computes that velocity from where on the toy the player clicked and calls `throw()` — direction from which half was clicked, power from distance to the ball's center vs. `TOY_RADIUS` (`THROW_MIN_SPEED`..`THROW_MAX_SPEED`), fully deterministic by design (the point is player control, unlike the pet's randomized throw). `physics_update(dt, ground_y, screen_width)` applies gravity, bounces off the ground (1–2 times, losing energy each bounce via `BOUNCE_DAMPING`/`WALL_DAMPING`) and reflects off both walls and the ceiling (always, not counted against the bounce budget) before settling. Add new item types by extending `COLORS` and the `if/elif` chains in `draw()`/`get_rect()`/`contains_point()` (and `physics_update()` if they should move).
  - **Toy kinds**: `item.kind` (only meaningful on the `TOY` type — `"ball"`, `"bone"`, ...) distinguishes multiple toys that share the exact same mechanics (throw/fetch/self-play, hit-testing, physics — all still `TOY_RADIUS`-circle-based regardless of kind) and differ only in `draw()`'s appearance, via `TOY_KIND_COLORS[kind]` for color and a kind-specific shape helper (`_draw_bone()` for `"bone"`; unrecognized/`None` kind falls back to the ball's circle). Add a new kind by giving it a color entry and, if it needs a distinct look, a `_draw_<kind>()` method plus a branch in `draw()`'s TOY case - no npc.py or hit-testing changes needed unless the new kind should behave differently, not just look different (a tug rope, planned next, is the first one that will: hold-and-grab tug-of-war instead of throw/fetch, so it'll need real new mechanics rather than just a new `kind`).
- **`npc_net.py`** — self-contained DQN implementation (`QNetwork`: 2 hidden layers of 64, `NPCAgent`: experience replay + target network + epsilon-greedy + `save`/`load`). No pygame/game-specific code here; it's a generic small DQN agent that `npc.py` drives.
- **`vocalizations.py`** — per-species vocabulary for the speech-bubble system (see npc.py's Vocalizations bullet): `VOCABULARY[species][emotion] = {"text": onomatopoeia, "emoji": ...}`. Only `DOG` exists so far. Deliberately kept out of `npc.py` so adding a cat/robot later means adding a new species entry here, not touching the (species-agnostic) selection logic in `npc.py`.
- **`wallet.py`** — the `Wallet` class: `self.currency`, `earn(amount)` (adds and immediately saves), `save()`/`load()` to/from `wallet.json` (in the project root, sibling to `saves/` - deliberately *not* inside `saves/`, since a pet could theoretically be named e.g. `wallet` and `_safe_name()` would produce a colliding filename there). Intentionally has no idea `npc.py`/pets exist - `npc.py` only ever computes and signals a reward amount (`fetch_delivered`/`fetch_reward_amount`), it never touches the wallet directly, keeping "the player's currency" and "a specific pet's state" as separate concerns that don't import each other.

Key constants live at the top of `npc.py` (gravity/ground, need rates/thresholds/drain rates, RL state/action sizes, sprite/animation settings, idle-activity hold-timer ranges, fetch-training tuning, fetch mini-game reward tuning) — most have a corresponding per-instance attribute set in `npc.__init__` (and listed in `PERSONALITY_FIELDS` if they should persist) for per-pet tuning. The idle-activity hold-timer ranges and `FETCH_AFFINITY_*`/`FETCH_REWARD_WINDOW`/`FETCH_STREAK_*`/`FETCH_AUTONOMOUS_REWARD_RATIO` constants are the exception — module-level only, not per-instance/persisted, since it's `self.fetch_affinity` (persisted) and `self.fetch_streak` (deliberately not, see Personality bullet) themselves - the *result* of applying these constants - that are per-instance, same relationship as e.g. `HUNGER_RATE` (global) vs. `self.hunger` (per-instance/persisted).

`saves/` is gitignored (per-player local data, not source), and so is `wallet.json` (same reasoning, just player- rather than pet-scoped - see wallet.py). `DogBundle/` is checked-in art assets, not gitignored.
